# SOP 審核準則

審核的目的：讓總部經管在送簽前，拿到一份「原單位照著改就能過」的意見。讀者是 SOP 撰寫單位與核准主管，他們會逐條核對原文，所以每一筆意見都必須指得到原文、講得出後果、給得出改法。寧可少而準，不要多而泛：一筆無法指認原文或只是文風偏好的意見，會讓整份報告失去可信度。

## 審核步驟

1. **通讀全文**，先判定 SOP 類別（Group Critical／Affiliate Critical／HQ Local／Affiliate Local）與語言型態。類別決定語言要求與核准者，判錯會連帶產生一串錯誤意見；無法判定時就標示「無法判定」並說明原因，語言與核准者相關項目改以「待向原單位確認」處理。
2. **逐項核對格式**：表頭九欄、八大章節、修改對照表。
3. **建立對照**：把全文的「誰（主體）／做什麼／何時（時限）／誰核准／留下什麼紀錄」整理起來，依〈標準〉第 6 節的對應關係逐一交叉比對。跨條文矛盾幾乎都是在這一步找到的。
4. **雙語文件逐條比對** 中英文。
5. **列出缺失**，每筆依下方欄位要求撰寫；合併重複，同一原因造成的多處問題寫成一筆並列出所有位置。
6. **自我檢查**：逐筆確認引文確實出現在文件中、嚴重度符合下方校準、建議沒有替公司發明制度。

## 十個審核面向

| 面向 | 要查什麼 | 典型缺失 |
|---|---|---|
| 格式與架構 | 表頭欄位齊全；八章章名、順序正確；修改對照表存在；編號連續 | 缺章、章名自創、跳號、流程未用四欄表格呈現 |
| 文件管制 | Control Number、Rev.、生效日、修訂日、核准人、制定人；Rev.≥2 有修訂紀錄；核准人與類別相符 | 編號空白、Rev.2 卻無修訂紀錄、Approved by 與簽核權限表不符 |
| 中英文一致性 | 同一條的中英文在主體、動作、強制程度（shall/must ↔ 應／須；should ↔ 宜；may ↔ 得）、數字、時限、範圍是否相同；Critical SOP 是否有缺譯段落 | 英文 within two months「initiate」而中文「完成」；表格只有英文 |
| 範圍與定義 | 適用主體與排除是否明確；全文縮寫、專有名詞是否有定義；定義章是否混入作業規定 | 範圍只寫「相關單位」；定義章內含時限與送簽流程；名詞未定義即使用 |
| 權責 | 每項工作有唯一負責單位；提出、審查、核准、執行是否分開；權責章與程序章的單位是否一致 | 兩個單位共同負責卻未分工；程序中出現權責章未列的角色 |
| 程序可執行性 | 每個步驟是否有：觸發條件、負責人、動作、產出、時限、交接對象；有無例外／退件／逾期處理 | 步驟無負責人；「核准後上傳」未說明誰上傳、多久內；退件後無下一步 |
| 管制重點與內控 | 控制點是否可稽核（有紀錄、有時限、有核准者）；申請與核准是否分離；例外是否需核准並留痕 | 控制點只是重述流程；無留存紀錄要求；例外處理空白 |
| 跨條文一致性 | 同一事項在不同條文的主體、數字、時限、核准者是否一致；引用的條號是否存在且內容相符 | 4.x 說「二個月內展開」而 7.x 說「二個月內簽核完成」；引用不存在的條文 |
| 用語與明確性 | 無法執行或稽核的模糊詞（及時、適時、相關單位、必要時、原則上）；同一對象前後用詞不同；錯字；「分公司」 | 「及時更新」未定義期限；Affiliate／Subsidiary／子公司／事業單位混用 |
| 時效與引用文件 | 寫死的年度、KPI、系統名稱、人名是否會過期；第 8 章文件是否齊全、有編號、與內文相符 | 內文提到的表單未列入第 8 章；引用已廢止文件 |

## 嚴重度校準

| 等級 | 判準 | 例子 |
|---|---|---|
| 重大 | 照此文件執行會導致核准權限錯置、控制失效，或文件缺少核心章節而無法作為制度依據 | 簽核權限表與管制重點對核准者的規定互相衝突；缺 Process 或 Control 整章 |
| 高 | 關鍵流程、權責、時限有缺漏或矛盾，執行者會做出不同解讀，稽核時無法判定是否符合 | 同一時限兩處數字不同；中英文強制程度相反；步驟無負責單位 |
| 中 | 造成執行歧義或增加溝通成本，但不致讓控制失效 | 模糊用語；名詞未定義；定義章混入流程；Critical SOP 局部缺譯 |
| 低 | 不影響實質要求的文字、格式問題 | 錯字、編號格式不一、用語不統一但意思清楚 |

`must_fix`（送簽前必改）：重大與高一律為 true；中、低僅在違反〈標準〉明文規定時為 true（例如表頭必填欄空白、Critical SOP 缺英文）。

## 每筆缺失的寫法

- **evidence**：一到數段原文，逐字照錄（含原有錯字、標點、中英文），並標示所在行號。只引用足以說明問題的最短片段，不要整段貼上。跨條文一致性與中英文一致性至少要有兩段引文（互相矛盾的兩處）。
- 「應有而沒有」的缺漏（缺章、缺欄位、缺步驟）：引用最接近的位置（例如該章章名、該步驟的前一步），並在 problem 中說明已檢查全文哪些地方都沒有。
- **problem**：具體說明哪裡不對，寫出兩處的差異或缺少的要素。不寫「不夠明確」這種無法據以修改的話。
- **impact**：照現況執行會發生什麼。用文件自身的情境推演，不引用文件外的案例、金額或法規。
- **recommendation**：原單位該做什麼。能直接改的，就在 suggested_text 給出可貼上的修正條文（雙語文件中英文都給）。
- 修正需要公司才知道的資訊（期限天數、核准層級、表單編號）時，不要代填數字，改用【待原單位確認：○○】標示，並把 basis 設為「待向原單位確認」。
- **basis**：`文件確認事實`＝問題可由引文直接看出（兩處數字不同、欄位空白）；`審核推論`＝需要推論才成立（此模糊用語可能造成…）；`待向原單位確認`＝取決於文件外的事實或原單位意圖。

## 不列為缺失的情況

這些是過去造成審核不準的主要來源：

- 文件擷取造成的現象：每頁重複的表頭、表格欄位在文字版錯位、流程圖無法以文字呈現、分頁造成的斷句。有附 PDF 原檔時以 PDF 版面為準。
- Local SOP 沒有英文。
- 首版文件的 Revised Date 空白、修改對照表無內容。
- 純文風偏好（句子可以更精簡、換個說法更好）。
- 文件沒有規定、而〈標準〉也沒有要求的事項（例如「建議增加 KPI」「應訂定罰則」）——除非缺少它會讓既有條文無法執行。
- 僅憑關鍵字相似就認定矛盾。先確認兩處談的是同一主體、同一情境；不同類別 SOP 的不同核准者不是矛盾。
- 同一問題的重複計列。

## 總結的寫法

- **summary**：三到五句，先講結論（可否送簽、主要障礙是什麼），再講整體品質。
- **priorities**：原單位應最先處理的三到五件事，依重要性排序，每項一句話並附缺失編號。
- **strengths**：文件確實做得好的地方（有才寫，一到三點）；沒有就留空。

審核意見是提供給核准主管的建議，不代表已核准。
